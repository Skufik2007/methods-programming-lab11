## Приложение

Чтобы контейнерам было чем обмениваться, сделан небольшой конвейер обработки измерений. Каждый язык выполняет свою роль:

```
                 POST /api/v1/batches                       GET /api/v1/reports
   клиент ───────────────► ingest (Go) ─┐        ┌──► reports (Python, FastAPI) ◄────── клиент
                                         │        │         volume :ro
                                         ▼        │
              ┌──────────── volume shared-data (/data) ────────────┐
              │  inbox/  ──►  processing/  ──►  outbox/ | failed/  │
              └────────────────────▲─────────────┬─────────────────┘
                                   │             │
                                   └ processor (Rust) — статистика по пакету
```

| Сервис | Язык | Что делает | Порт |
|---|---|---|---|
| `ingest` | Go (net/http) | принимает пакет чисел, проверяет и атомарно кладёт в `inbox/`; отдаёт статус пакета | 8081 → 8080 |
| `processor` | Rust | забирает пакеты, считает среднее, медиану, p95/p99, σ и гистограмму, пишет отчёт в `outbox/` | 9090 (только внутри сети) |
| `reports` | Python (FastAPI) | читает отчёты из volume (монтирует **только на чтение**) и отдаёт их по HTTP, Swagger — `/docs` | 8082 → 8000 |

## Запуск

```bash
# локальная сборка всех образов и запуск
docker compose up --build --wait

# или готовые образы из GitHub Container Registry (публичные)

curl -s localhost:8081/api/v1/batches -d '{"name":"sensor-1","values":[1.5,2,3.25,10]}'

curl -s localhost:8082/api/v1/reports

```

## Описание решения

### Средн. №3. Dockerfile для Rust-приложения

[`processor/Dockerfile`](processor/Dockerfile) — двухэтапная сборка:

1. **Сборка на `rust:1.99-alpine`** (закреплён по digest). Alpine использует musl, и Rust под `x86_64-unknown-linux-musl` по умолчанию собирает **полностью статический бинарь**: ему не нужны ни glibc, ни динамический загрузчик.
2. **Финальный образ `FROM scratch`** — пустой: только бинарь и каталог `/data`. Ни shell, ни пакетного менеджера, ни библиотек, поэтому уязвимостям в системных пакетах просто неоткуда взяться.

Дополнительно:
- **Профиль release:** `lto = true`, `codegen-units = 1`, `strip = true`, `panic = "abort"`. Бинарь весит около 800 КБ, **образ — 849 КБ**.
- **Healthcheck без curl.** В `scratch` нет curl, поэтому healthcheck выполняет сам бинарь (`/processor healthcheck` делает HTTP-запрос к своему `/health` через `TcpStream`).
- **Непривилегированный пользователь** `10001`. Сигнал SIGTERM от `docker stop` обрабатывается (crate `ctrlc` с `termination`): текущий пакет дорабатывается, процесс выходит. В CI остановка занимает меньше секунды, без SIGKILL.
- **Восстановление после сбоя.** Пакет, который пролежал в `processing/` дольше `PROCESSING_TIMEOUT_SEC` (5 минут), возвращается в `inbox/`: при старте и затем раз в минуту. Так подхватываются пакеты упавшего экземпляра и пакеты, для которых не удалось записать отчёт, а пакеты, которые сейчас обрабатывает другой экземпляр, не трогаются. Время отсчитывается от захвата: при захвате processor обновляет mtime файла.
- **Огромные значения.** Статистика считается в масштабированных значениях, поэтому `[1e300, −1e300]` и даже `[−1e308, 1e308]` обрабатываются без переполнения промежуточных величин. Если результат не помещается в f64 (сумма `1e308 + 1e308`), пакет уходит в `failed/` с причиной, а не записывается отчётом с `null`.

Go и Python упакованы так же многоэтапно: Go — статический бинарь (`CGO_ENABLED=0`) в `scratch`, Python — venv из этапа сборки в `python:3.12-slim`.

### Средн. №5. docker-compose.yml с Python, Go и Rust сервисами

[`compose.yaml`](compose.yaml):
- Три сервиса в общей сети **`lab11-pipeline`**. `processor` наружу не публикуется (`expose`, а не `ports`): его `/health` и `/metrics` доступны только внутри сети.
- **Healthcheck у каждого образа.** `reports` стартует после того, как `processor` стал healthy (`depends_on: condition: service_healthy`). `docker compose up --wait` ждёт готовности всех сервисов.
- **Общие настройки вынесены в якорь `x-service`:** политика перезапуска, сеть, ротация логов и `stop_grace_period: 20s` — больше тайм-аутов остановки самих сервисов (ingest ждёт запросы до 15 с), поэтому Docker не присылает SIGKILL раньше времени.
- **Каждый сервис описан и с `build`, и с `image`:** одна и та же конфигурация собирает образы локально или запускает опубликованные (`TAG=sha-… docker compose pull`). Так работает e2e в CI.

### Средн. №7. Обмен данными через volume

Именованный volume **`shared-data`** смонтирован во все три контейнера:

| Сервис | Монтирование | Доступ |
|---|---|---|
| ingest | `shared-data:/data` | пишет в `inbox/` |
| processor | `shared-data:/data` | `inbox/ → processing/ → outbox/` или `failed/` |
| reports | `shared-data:/data:ro` | только читает `outbox/` и `failed/` |

Чтобы обмен через файлы был надёжным, соблюдаются несколько правил.

- **Атомарная запись.** Файл пишется во временный `.<имя>.tmp`, затем `fsync` и `rename` в итоговое имя. Rename в пределах одной файловой системы атомарен, поэтому читатель видит либо ничего, либо полный файл. Файлы с точкой в начале имени все сервисы пропускают.
- **Захват пакета через rename** `inbox/x.json → processing/x.json`. Если запустить несколько экземпляров processor, один пакет достанется ровно одному из них: rename у второго вернёт `NotFound`. Восстановление после сбоя возвращает в очередь только «зависшие» пакеты, поэтому не отнимает работу у живого экземпляра.
- **Статус пакета без гонки.** ingest ищет пакет по каталогам в порядке его движения (`inbox → processing → outbox | failed`): если processor перенёс файл между двумя проверками, следующая проверка его найдёт. Тест переносит пакет на следующий этап после каждой возможной проверки.
- **Проверка формата при чтении.** reports проверяет каждый файл моделями Pydantic (`reports/app/models.py`): конечные числа, обязательные поля. Повреждённый файл пропускается с одной записью в лог и учитывается в `/api/v1/summary` (`invalid_files`), а не ломает весь список отчётов.
- **Права доступа.** Все сервисы работают от пользователя `10001`. В каждом образе `/data` создаётся с владельцем `10001` (`COPY --chown`), и при первом подключении пустого именованного volume Docker копирует туда владельца из образа. В CI в volume видно `drwxr-xr-x 10001 10001` для всех подкаталогов.
- **Проверка готовности.** `/health/ready` у ingest проверяет, что в volume можно писать, у reports — что `outbox/` доступен для чтения.

Сквозной тест [`deploy/e2e.py`](deploy/e2e.py) отправляет 5 пакетов от 10 до 5000 значений, ждёт, пока processor их обработает, и сверяет статистику из отчёта с эталоном модуля `statistics` Python с точностью `1e-9`. Пакет `[1e300, −1e300]` должен обработаться, пакет с суммой вне f64 — уйти в `failed/`, а список отчётов — продолжать работать. Затем тест проверяет, что `inbox/` и `processing/` пусты.

### Повыш. №3. CI/CD: сборка и публикация образов трёх языков

[`.github/workflows/images.yml`](.github/workflows/images.yml):

| Событие | Что происходит |
|---|---|
| pull request | все три образа собираются (проверка Dockerfile), не публикуются |
| push в `main` | публикация в GHCR с тегами `sha-<коммит>` и `latest` |
| тег `v1.2.3` | дополнительно теги `1.2.3` и `1.2` |

- Сборка идёт **матрицей** по трём сервисам параллельно, через `docker/build-push-action` и buildx. Теги и OCI-метки (`org.opencontainers.image.source`, `revision`, …) формирует `docker/metadata-action`.
- Публикация выполняется встроенным `GITHUB_TOKEN` с правом `packages: write`. **Личных токенов и секретов в репозитории нет.**
- Коммиты, меняющие только документацию (`*.md`), образы не пересобирают.
- **Проверяется то, что опубликовано:** job `e2e` скачивает из GHCR образы именно этого коммита (`sha-<коммит>`), поднимает compose, прогоняет сквозной тест, показывает содержимое volume и размеры образов и проверяет остановку по SIGTERM.

Отдельный workflow [`ci.yml`](.github/workflows/ci.yml) запускает тесты и линтеры каждого сервиса (gofmt, go vet, `go test -race`; rustfmt, clippy `-D warnings`, cargo test; ruff, pytest), **hadolint** для всех Dockerfile и проверку кеша слоёв.

### Повыш. №5. Оптимизация слоёв для максимального кэширования

Принципы, применённые во всех трёх Dockerfile:

0. **Базовые образы закреплены по digest** (`rust:1.99-alpine@sha256:…`): тег со временем начинает указывать на другой образ, а с ним меняется и кеш всех слоёв. Digest делает и кеш, и результат воспроизводимыми.
1. **Сначала зависимости, потом код.** Копируются только манифесты (`go.mod/go.sum`, `Cargo.toml/Cargo.lock`, `requirements.txt`), ставятся зависимости, и только потом копируется код. Правка кода не инвалидирует слой зависимостей.
2. **Rust: сборка зависимостей с заглушкой.** Cargo не умеет «скачать и собрать только зависимости», поэтому проект собирается с пустым `fn main() {}`. Слой с 24 скомпилированными крейтами зависит только от `Cargo.toml/Cargo.lock`. После копирования настоящего кода пересобирается один крейт. `touch src/main.rs` защищает от ловушки: COPY сохраняет время изменения файла, и cargo мог бы решить, что пересобирать нечего.
3. **BuildKit cache mounts** для того, что не должно попадать в образ, но полезно между сборками: реестр крейтов (`/usr/local/cargo/registry`), модули и кеш компиляции Go (`/go/pkg/mod`, `/root/.cache/go-build`), кеш pip.
4. **`.dockerignore` по принципу «запрещено всё, кроме нужного».** В контекст попадают только файлы, которые использует Dockerfile. Правка README, тестов или локальный `target/` не сбрасывает кеш и не раздувает контекст.
5. **Порядок от редко меняющегося к часто меняющемуся** в финальном образе Python: базовый образ → venv (51.7 МБ) → `/data` → код (7.6 КБ). Обновление кода передаёт по сети только последний слой в 7.6 КБ.
6. **Многоэтапность.** Компиляторы, заголовки, pip-кеш и промежуточные файлы остаются в этапе сборки.
7. **Кеш между запусками CI:** `cache-to: type=gha,mode=max` сохраняет и промежуточные этапы (`mode=max`), отдельно для каждого сервиса (`scope`).

**Измерение** ([`ci/cache-check.sh`](ci/cache-check.sh), job «Кеш слоёв Docker» в CI). Каждый образ собирается с нуля, затем ещё раз без изменений, затем после правки одного файла кода. Job падает, если при повторной сборке без изменений хотя бы один шаг `RUN` выполнился заново или если слой зависимостей после правки кода не взят из кеша. Результаты на runner GitHub Actions:

| Образ | С нуля | Без изменений | После правки кода | Слой зависимостей из кеша | Размер образа |
|---|---:|---:|---:|:---:|---:|
| ingest (Go) | 24.8 с | 0.3 с | **1.7 с** | да | 7.58 МБ |
| processor (Rust) | 36.9 с | 0.3 с | **11.5 с** | да | **849 КБ** |
| reports (Python) | 10.2 с | 0.3 с | **0.7 с** | да | 171 МБ |

Пересборка после правки кода у Go и Python быстрее примерно в 15 раз, у Rust — в 3.2 (оставшиеся 11 с — это компиляция с LTO самого processor). Сборка processor в CI с кешем GHA заняла 33 с против 1 мин 47 с при первом запуске.

#### Размеры образов

| Образ | База | Размер | Что внутри |
|---|---|---:|---|
| processor (Rust) | `scratch` | **849 КБ** | статический musl-бинарь |
| ingest (Go) | `scratch` | 7.58 МБ | статический бинарь (`-trimpath -ldflags="-s -w"`) |
| reports (Python) | `python:3.12-slim` | 171 МБ | интерпретатор и стандартная библиотека (~120 МБ), venv с FastAPI/uvicorn (52 МБ), код (8 КБ) |

Компилируемые Go и Rust помещаются в пустой образ. Python-сервису нужен интерпретатор, поэтому его образ на два порядка больше. Дальнейшее уменьшение возможно через distroless-python или Alpine, но с риском несовместимости колёс, собранных под glibc.

## Итоги

- Три сервиса на трёх языках, обмен данными через общий volume с атомарной записью и захватом файлов через rename.
- Тесты: Go — 6, Rust — 14, Python — 10, плюс сквозной тест опубликованных образов в CI (включая экстремальные значения).
- CI/CD публикует образы всех трёх языков в GHCR и проверяет именно опубликованные образы.
- Оптимизация слоёв подтверждена измерением: после правки кода слой зависимостей берётся из кеша во всех образах, пересборка в 3–15 раз быстрее холодной.
