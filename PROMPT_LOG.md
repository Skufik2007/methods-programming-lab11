## Исходная постановка задачи

> Выполни лабораторные работы №10 и №11 по варианту 3, уровень — повышенный. Если в методичке не сказано иное, каждая работа — в отдельном публичном репозитории. Учти все замечания, которые проверяющий дал к ЛР №9: PROMPT_LOG, атомарные коммиты, комментарии к неочевидным решениям.

Принятые мной решения по ходу работы:
- **Проверять контейнеры в GitHub Actions**, а не ставить Docker Desktop: на системном диске мало места, а логи CI заодно служат доказательством работоспособности.
- **Сверить задания с обновлённой таблицей**, которую прислал проверяющий. Для варианта 3 задания ЛР №11 не изменились.
- **Провести строгое ревью перед отправкой.** Попытка сдачи одна, поэтому я поручил проверить работу по критериям, которые проверяющий применил к ЛР №9, и исправить всё найденное.

Чтобы обмен данными между контейнерами был содержательным, AI предложил небольшой конвейер: Go (`ingest`) принимает пакеты измерений → Rust (`processor`) считает статистику → Python (`reports`) отдаёт отчёты. Сервисы обмениваются файлами через общий volume. Предложение принято.

## Записи по заданиям варианта 3

### 1. Средн. №3 — Dockerfile для Rust-приложения

| | |
|---|---|
| **Задача для AI** | Упаковать Rust-сервис в минимальный образ. |
| **Что предложил AI** | Сборка на `rust:alpine` (musl, полностью статический бинарь) и финальный образ `FROM scratch`: только бинарь и каталог данных, образ около 850 КБ. Healthcheck — подкоманда самого бинаря, потому что curl в пустом образе нет. Непривилегированный пользователь, обработка SIGTERM. |
| **Принято** | Схема образа целиком. |
| **Изменено после проверки** | При первом запуске в CI сервисы получили `permission denied` на volume: `COPY --from` не переносит владельца, и каталог принадлежал root. Добавлен `COPY --chown=10001:10001`. **На итоговом ревью:** базовый образ закреплён по digest. |
| **Как проверено** | Сквозной тест опубликованного образа в CI; права в volume видны в логе (`10001 10001`). |

### 2. Средн. №5 — docker-compose с Python, Go и Rust сервисами

| | |
|---|---|
| **Задача для AI** | Поднять три сервиса одной командой. |
| **Что предложил AI** | Общая сеть, processor наружу не публикуется, reports стартует после healthy processor. Общие настройки вынесены в якорь `x-service`. Каждый сервис описан и с `build`, и с `image`, поэтому одна конфигурация работает и с локальной сборкой, и с образами из реестра. |
| **Принято** | Структура compose. |
| **Изменено на итоговом ревью** | Docker по умолчанию шлёт SIGKILL через 10 с, а ingest ждал запросы до 15 с. Задан `stop_grace_period: 20s`, тайм-ауты сервисов вынесены в переменные окружения. |
| **Как проверено** | `docker compose up --wait` в CI; остановка по SIGTERM без SIGKILL. |

### 3. Средн. №7 — volume для обмена данными между контейнерами

| | |
|---|---|
| **Задача для AI** | Обмен файлами между сервисами через общий volume. |
| **Что предложил AI** | Каталоги `inbox → processing → outbox / failed`. Атомарная запись (временный файл, fsync, rename), захват пакета через rename (два экземпляра не возьмут один пакет), reports монтирует volume только на чтение. |
| **Принято** | Протокол обмена. |
| **Изменено после проверки** | Clippy указал на неиспользуемое поле `id` — из него сделана проверка, что содержимое файла совпадает с его именем. **На итоговом ревью найдено и исправлено:** <br>• пакет с огромными значениями (`1e308`) давал в статистике `null`, после чего список отчётов в Python отвечал 500 всем — теперь статистика считается без переполнения, а непредставимый результат уходит в `failed/`; <br>• reports не проверял формат файлов — теперь каждый файл проверяется моделью, повреждённый пропускается; <br>• статус пакета проверялся в обратном порядке каталогов, и при гонке с processor мог прийти ответ «не найден»; <br>• при старте processor возвращал в очередь и пакеты, которые обрабатывал другой экземпляр — теперь только «зависшие» дольше 5 минут. |
| **Как проверено** | Сквозной тест сверяет статистику с эталоном модуля `statistics` до `1e-9`, проверяет экстремальные значения и работу списка отчётов. Отдельный тест переносит пакет на следующий этап после каждой возможной проверки статуса. |

### 4. Повыш. №3 — CI/CD, который собирает и пушит образы всех трёх языков

| | |
|---|---|
| **Задача для AI** | Автоматическая сборка и публикация образов. |
| **Что предложил AI** | Матрица из трёх сервисов, публикация в GitHub Container Registry встроенным `GITHUB_TOKEN` (без личных секретов). Теги `sha-<коммит>`, `latest`, semver. Кеш слоёв между запусками. Отдельный job скачивает **опубликованные** образы этого коммита и прогоняет на них сквозной тест. |
| **Принято** | Схема публикации и проверка именно опубликованных образов. Благодаря ей ошибка с правами на volume была найдена до сдачи. |
| **Изменено на итоговом ревью** | Коммиты, меняющие только документацию, образы не пересобирают. |

### 5. Повыш. №5 — оптимизация слоёв Docker для максимального кэширования

| | |
|---|---|
| **Задача для AI** | Минимизировать пересборку при изменениях. |
| **Что предложил AI** | Зависимости — отдельным слоем до кода. Для Rust зависимости собираются с заглушкой `main.rs` (`touch` защищает от устаревшей метки времени после COPY). BuildKit cache mounts, `.dockerignore` по принципу «запрещено всё, кроме нужного», кеш GHA между запусками CI. Скрипт `ci/cache-check.sh` измеряет сборки и роняет job, если кеш не сработал. |
| **Принято** | Все приёмы и обязательная проверка в CI. |
| **Изменено на итоговом ревью** | Проверка повторной сборки ужесточена: раньше хватало одного шага из кеша, теперь из кеша обязаны взяться все шаги `RUN`. Базовые образы закреплены по digest, иначе кеш зависит от того, куда сейчас указывает тег. |
| **Результат** | После правки кода пересборка Go и Python быстрее примерно в 15 раз, Rust — в 3,2 раза. Слой зависимостей во всех трёх образах берётся из кеша. |

## Итоговое ревью перед сдачей

Перед отправкой по моему поручению проведено ревью по критериям проверяющего. Найдено 10 недостатков, все исправлены отдельными коммитами с тестами: 4 важных (экстремальные значения ломали список отчётов, отсутствие проверки формата в reports, гонка при определении статуса, структура этого файла), 4 средних и 2 мелочи. Кроме того, по моей просьбе сообщения коммитов приведены к единому стилю Conventional Commits; код и даты коммитов при этом не менялись.

## Итоги

- Все пять заданий варианта выполнены. Тесты: Go — 6, Rust — 14, Python — 10, плюс сквозной тест опубликованных образов в CI. CI и публикация образов зелёные.
- Главный вывод о работе с AI: типовые приёмы Dockerfile и CI он применяет уверенно, но ошибки на стыке сервисов (права на volume, `null` вместо числа между Rust и Python, гонка при чтении каталогов) находятся только запуском и целенаправленным ревью. Поэтому решающими были сквозной тест на опубликованных образах и отдельная проверка перед сдачей.
